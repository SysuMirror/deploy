# 脚本部署（非部署台应用）

> 网页下发宿主命令的能力：把宿主机上已有的部署 / 测试脚本注册成「应用」，
> 填几个参数点一下就执行，不用为它们接一整套容器化部署流水线，也不用手敲命令。
>
> 入口：`控制台 → 脚本部署`（`/scripts`，也支持根路径部署的 `/deploy/scripts`）

---

## 1. 它解决什么问题

平台原本的部署链路是「模块 → 打包/拉代码 → 注入 K8s/容器 → 配路由」，
适合长期跑的 Web 服务。但有些东西不属于这个模型：

- 别人已经写好、跑得好好的脚本（例如 `iWiki/iwiki.py` 的一键部署）；
- 一次性的运维动作（发版、回滚、清缓存、刷数据）；
- 需要以「宿主视角」执行、依赖宿主环境的命令（宿主那套 python / docker / git）。

这些脚本此前只能 SSH 上去手敲。本功能把它们搬到网页：**注册命令 + 填参数 + 看实时输出**。

关键设计取向：**不给这类应用做流水线**。没有构建、没有镜像、没有 K8s 资源，
就是「cd 到根目录，把用户配置的命令拼出来执行」。简单可靠优先。

## 2. 数据模型

五张表（`apps/deploy-api/src/db/init.ts` 的 `ensureScriptTables()`）：

| 表 | 说明 |
| --- | --- |
| `script_apps` | 应用：名称、说明、**根目录 workdir**、是否启用、创建者 |
| `script_commands` | 命令组：`name` 为命令名（自由命名），`main_command` 为用户自填的命令主体 |
| `script_params` | 命令组的参数预设：`flag`、显示名、默认值、是否必填、取值方式、输入类型、候选项 |
| `script_app_members` | 成员：`role` 为 `owner`（创建者）/ `member`（自助加入） |
| `script_runs` | 执行记录：命令组名快照、最终命令行、参数快照、状态、退出码、完整输出 |

层级关系：`script_apps` → `script_commands` → `script_params`。

**一个应用下可以有任意多个命令组**（如「部署到测试」「部署到生产」「查看状态」「回滚」），
同应用内命令组名不允许重复 —— 重名会让「执行」无法区分要跑哪条。

命令与参数由外键级联删除；`script_runs` **不挂外键**，删应用后历史仍可追溯。

> 迁移说明：早期版本用 `kind`（`deploy`/`test`）标识命令且每类只允许一条。
> 现在改为自由命名的命令组，启动时自动迁移：
> `script_commands.kind` → `name`、`script_runs.kind` → `command_name`，
> 老值按语义映射成「部署」「测试」；同时把每个应用的创建者补进成员表，
> 避免升级后创建者自己反而执行不了（`migrateScriptCommandNaming()` + `backfillScriptAppOwners()`）。

删除应用时的级联（命令组 / 参数 / 成员）依赖 `db.pragma('foreign_keys = ON')`
（`init.ts` 第 14 行，better-sqlite3 是单连接，进程内全局生效）。
注意：**`sqlite3` 命令行走 CLI 时外键默认是关的**，从 CLI 手工删数据不会触发级联，
会留下孤儿行 —— 详见 §9 排障表。

## 3. 命令行拼接规则

这是本功能的核心约定，前后端各实现一份（后端执行、前端即时预览），
规则必须一致：

```
命令主体 + 参数名1 + 参数值1 + 参数名2 + 参数值2 ...
```

| 情况 | 行为 |
| --- | --- |
| 命令主体 | **原样**保留，允许写 `cd .. && python3 xxx.py` 这类带 shell 语义的串 |
| 参数取值方式 `value` | 拼 `--flag 值` |
| 参数取值方式 `switch` | 只拼 `--flag`（勾选才拼，适合 `--dry-run` 这类开关） |
| 值为空 | **整个参数跳过** —— 这就是「参数可选」的实现方式 |
| 必填但为空 | 报错 `参数「xxx」为必填`，不执行 |
| 值含空格 / 引号 | 做 shell 单引号转义（`'` → `'\''`），所以 `rel 1.0` 不会被拆成两个词 |

实际执行时前端展示的是完整脚本：

```
cd '/root/SSE_Market/iWiki' && python3 iwiki.py deploy --target 'test' --release 'rel 1.0' --dry-run
```

**参数名做白名单校验**（`-x` / `--xxx` / `xxx`，只允许字母数字与 `-` `_`），
避免用户把任意内容当参数名写进去变成命令注入。

## 4. 执行机制（为什么这么绕）

### 4.1 不在容器里直接跑

`deploy-api` 容器非特权，只挂载了 `sse-sdpy` 自身目录，
既看不到 `/root/SSE_Market` 下的其他项目，也不保证装了宿主那套 python / docker / git 版本。
在容器里 `spawn` 会「找得到命令但版本/路径全错」，是最难查的一类问题。

### 4.2 用「特权辅助容器 + nsenter 进宿主命名空间」

与既有的进程管理 `killViaHost` 同一套路（都是 `docker run --pid=host --privileged`）：

```bash
docker run --rm --name sdpy-script-<runId> --pid=host --privileged <image> \
  nsenter -t 1 -m -u -i -n -p -- sh -c "cd '<workdir>' && <命令行>"
```

`nsenter` 之后就是宿主的挂载 / 网络 / PID 命名空间，**等于直接在宿主上执行**：
脚本里写的 `docker`、宿主 python3、宿主 `.env` 全部可用。

- 不给辅助容器挂任何卷 —— 宿主根文件系统已经通过 `-m` 拿到了；
- 用 `execFile`/`spawn` 传数组参数（不经过本地 shell），所以命令行里的引号不会被二次解释；
- 镜像可配（`SCRIPT_RUN_IMAGE`，默认 `busybox:latest`，只需带 `nsenter`）。

### 4.3 终止与清理

- **取消执行**：kill 本地 `docker` 客户端**不会**带走容器，必须
  `docker rm -f sdpy-script-<runId>` 才真正终止（`killContainer()`）；
- 正常结束用 `--rm` 自动收摊；
- 超时兜底（`SCRIPT_RUN_TIMEOUT_MS`，默认 60 分钟）同样走 killContainer；
- 服务启动时 `cleanupOrphanContainers()` 清掉上次进程被杀后残留的执行容器，
  并把库里遗留的 `running` 记录标记为 `interrupted`
  —— 否则宿主上会一直挂着孤儿容器。

### 4.4 实时输出

输出走 SSE：`POST /api/v1/scripts/runs/:runId/stream`。

用 POST 而不是 GET，是为了能带 `Authorization` 头
（`EventSource` 既不能设 header 也不支持 POST），前端用 `fetch` + `ReadableStream` 读，
与 `modules.ts` 的 `generate-deploy-sh/stream` 保持一致。

订阅时先回放已产生的输出，所以中途接入 / 刷新页面不会看到空白。

> ⚠️ **踩坑记录（已修）**：SSE 的断连监听必须挂 `res.on('close')`，**不能挂 `req.on('close')`**。
> 对 POST 请求，Node 在**请求体读完**时就会让 `req` 触发 `close`（这并不代表客户端断开），
> 挂在 `req` 上会导致「刚推完 meta/replay 就自己把流关掉」——
> 现象是前端一点输出都收不到，但历史记录里结果又是对的，很容易误判成前端问题。

## 5. 权限模型

### 5.1 成员制：加入应用才能执行

| 操作 | 谁可以 |
| --- | --- |
| 查看应用列表 / 执行历史 | 全体开发者（平台已开发者门禁） |
| **执行命令** | **该应用的成员**、创建者、平台管理员 |
| 加入应用 | 全体开发者（自助，无需审批） |
| 退出应用 | 成员自己（**创建者不能退出**，否则应用会变成无人可管） |
| 新建应用 | 全体开发者（创建者自动成为 owner 成员） |
| 修改 / 删除 / 管成员 | **仅创建者或平台管理员** |

取舍说明：

- **执行设成员门槛**：应用里的命令是能改宿主状态的部署脚本（重启容器、拉代码）。
  不设门槛时任何人顺手点一下就能触发别人的生产部署，出了事也说不清是谁的意图；
  成员制把「能跑」收敛成一个显式动作（加入），且页面会记录谁执行的。
- **加入不设审批**：开发者门禁已经在入口把过一道；再叠审批会让「临时帮忙跑一次部署」
  变成要走流程的事，反而促使大家绕开平台去手工执行。成员列表公开可见，
  创建者可以随时移除，不想要谁加入就移掉。
- **改命令必须限制**：改命令等于改别人的部署行为，只有创建者与平台管理员能动。

后端 `canRun()` / `canManage()` 分别判定两种能力，
`listApps()` 会给每个应用算出 `canRun` / `canManage` / `joined` 三个布尔位给前端，
所以页面能精确渲染「加入应用以执行」还是「执行 xxx」，而不是给一堆点了会报错的按钮。

所有写操作（建/改/删/执行/终止/加入/退出/移除成员）都写 `audit_logs`，审计页可查。

### 5.2 其他几道闸

- 根目录**白名单**：`SCRIPT_ALLOWED_ROOTS`（默认 `/root/SSE_Market`）。保存应用时会
  **进宿主机命名空间**做两步校验：
    1. 先做纯字符串规范化，`/root/SSE_Market/../etc` 这种 `..` 穿越直接拒；
    2. 再 `readlink -f` 解析真实路径，解析结果也必须落在白名单内。

  为什么非要第 2 步：字符串前缀挡不住白名单目录里的**符号链接**。比如
  `/root/SSE_Market/xxx → /etc` 在字符串层面完全合法，`cd` 进去却在白名单之外。
  而解析必须在宿主命名空间做 —— deploy-api 是非特权容器，容器里的
  `/root/SSE_Market` 是镜像内的另一个目录，在 Node 进程里 `realpath` 看到的是容器的文件系统，
  校验等于没做。所以这里复用了执行器的「特权容器 + `nsenter`」机制（见 `services/host-exec.ts`）。

  校验通过后**落库的是解析后的路径**，不是用户原始输入：这样界面上的
  `宿主机 <目录>` 与执行时 `cd` 进去的目录严格一致，不会出现「看着在 A、其实在 B」。
  目录不存在会明确提示「根目录不存在」，解析后越界会提示「根目录解析后不在允许范围内」。
- 并发上限 `SCRIPT_RUN_MAX_CONCURRENT`（默认 3）—— 脚本可能装依赖 / 占端口；
- 单次输出上限 512KB（防止 `yes` 之类把库写爆），超出截断并注明；
- 应用可「停用」，停用后不能执行。

## 6. 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SCRIPT_ALLOWED_ROOTS` | `/root/SSE_Market` | 允许作为根目录的路径白名单，逗号分隔 |
| `SCRIPT_RUN_IMAGE` | `busybox:latest` | 执行用辅助容器镜像（需带 `nsenter`） |
| `SCRIPT_RUN_TIMEOUT_MS` | `3600000`（60 分钟） | 单次执行超时，到点强制终止 |
| `SCRIPT_RUN_MAX_CONCURRENT` | `3` | 同时执行上限 |

`deploy-api` 容器**需要能调用 `docker`**（`/var/run/docker.sock` + `/usr/bin/docker` 已挂载），
这是本功能的前置条件 —— 与既有的容器管理 / 进程 kill 共用同一依赖。

## 7. API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/scripts` | 应用列表（含命令组与参数定义、权限位） |
| POST | `/api/v1/scripts` | 新建应用（创建者自动成为 owner） |
| GET | `/api/v1/scripts/:id` | 单应用（含成员列表）+ 最近执行历史 |
| PUT | `/api/v1/scripts/:id` | 更新应用（命令组与参数**整组替换**） |
| DELETE | `/api/v1/scripts/:id` | 删除应用 |
| POST | `/api/v1/scripts/:id/join` | 加入应用（自助，幂等） |
| POST | `/api/v1/scripts/:id/leave` | 退出应用（创建者不能退） |
| GET | `/api/v1/scripts/:id/members` | 成员列表 |
| DELETE | `/api/v1/scripts/:id/members/:userId` | 移除成员 |
| POST | `/api/v1/scripts/:id/preview` | 只拼接不执行，返回完整命令行 |
| POST | `/api/v1/scripts/:id/run` | 执行（需为成员），返回 `runId` |
| POST | `/api/v1/scripts/runs/:runId/stream` | SSE 实时输出 |
| POST | `/api/v1/scripts/runs/:runId/cancel` | 终止执行 |
| GET | `/api/v1/scripts/:id/runs` | 执行历史 |
| GET | `/api/v1/scripts/runs/:runId` | 单次执行详情（含完整输出） |

更新应用采用「整组替换命令组与参数」而不是增量 diff：
编辑弹窗提交的就是完整定义，整替比 diff 更不容易出现「改了一半」的中间态。

## 7.1 输出高亮与复制

前端 `apps/deploy-web/src/utils/ansi.ts` 负责把原始输出渲染成带颜色的 HTML。

**两层高亮**：

1. **ANSI 转义序列**：脚本自己带的颜色（`\033[0;36m` 这类）。
   支持 8 基本色 / 8 亮色前景、粗体、暗色；背景色与光标移动等控制码忽略
   —— 终端日志里几乎不用，画出来反而花。
2. **语义关键字**：日志里没上色的 `error` / `[失败]` / `warning` / `success` / `[完成]` 等，
   按失败（红）→ 警告（黄）→ 成功（绿）→ 提示（蓝）的优先级整行着色。

两种情况下**不做**语义着色，都有明确理由：

- 整行已有 ANSI 颜色时：尊重脚本自己的配色，否则会出现「脚本标绿、我们又把整行刷红」的打架效果；
- **命令行回显行（`$ ...`）**：那是命令本身而非日志内容，
  命令里出现 `grep error` 会让整行变红，误导排查方向。

**复制**分三处，都是纯文本：

| 位置 | 内容 |
| --- | --- |
| 控制台「复制全部」 | 整段输出，**去掉 ANSI 控制码** |
| 「即将执行的命令」复制 | 拼接后的完整命令行 |
| 执行历史每条右侧复制 | 该次的命令行 + 命令组 + 工作目录 |

> ⚠️ **安全前提**：输出是用户脚本产生的**任意内容**，`v-html` 前必须 HTML 转义。
> `renderAnsi()` 的顺序是**先转义再拼标签**，所以输出里即便写了
> `<img src=x onerror=alert(1)>` 或 `</span><script>...</script>` 也只会当文本显示
> （已用攻击载荷回归验证：渲染结果只可能包含 `<span>` 一种标签）。
> 复制走后端 `stripAnsi()` 的等价前端实现，避免粘出去是一堆 `[0;36m`。

## 7.2 「跑的什么命令、在哪跑的」必须一眼可见

这个功能跑的是**能改宿主状态的脚本**，出问题时第一句话必然是「刚才到底在哪个目录跑了什么」。
所以这几个信息在链路上处处显式给出，不靠用户自己拼：

| 位置 | 展示内容 |
| --- | --- |
| 应用卡片 | `宿主机 <workdir>` —— 让人先建立「这台机器上、这个目录」的概念 |
| 抽屉头部 | `宿主机 · <workdir>` |
| 抽屉「执行位置」面板 | 宿主机标签 + 路径（可一键复制）+ 一句说明：命令经 `nsenter` 进宿主命名空间执行，**不是跑在平台容器里**（这解释了为什么宿主 python3 / docker 都能用） |
| 抽屉「即将执行的完整命令」 | 拆成 **目录** / **命令** 两行（比一整条长串好核对），下面注明实际下发的是 `cd '<workdir>' && …` |
| 控制台首行 | `$ cd '<workdir>' && <命令>`，紧跟 `[命令组] xxx`、`[执行位置] 宿主机 <workdir>` |
| 执行历史每条 | `cd '<workdir>' && <命令>`，不点进去就知道每条跑了什么、在哪跑的 |
| 复制 | 三处复制给的都是**含 `cd` 的完整脚本**，可直接粘到终端复现 |

两个细节值得记一笔：

- **历史里必须带 `&&`**：只并排显示 `cd /a/b` 和 `pwd && date` 会被读成一条命令，
  看着像 `cd /a/b pwd && date`，所以把 `cd '<dir>' &&` 作为整体一起显示（目录部分用青色区分）。
- **时间要按本地时区渲染**：后端存的是 `toISOString()`（UTC），
  早先用 `t.slice(0,19)` 直接切字符串，页面会把北京时间显示成 UTC ——
  差 8 小时，用户看到「刚跑完的记录是 8 小时前」会以为平台坏了。
  现与 `MonitorLogView` / `ProcessView` 一致，用 `new Date(...)` 后取本地时间。

## 8. 页面怎么用

页面分成**列表页**和**详情页**两层（与「项目」页的浏览习惯一致）：
列表页只回答「有哪些应用」，点卡片进详情页才看命令组、执行、管成员。

> 为什么不用「一页铺开」：早期版本把根目录、全部命令组、每个命令组的执行按钮
> 全塞在一张卡片里 —— 一个应用 4 个命令组就是 4 个「执行 xxx」按钮，
> 卡片又高又挤，手机上更难扫，也不像平台其它页面。
> 现在卡片是**整张可点**的导航入口，执行按钮收进详情页。

**列表页（`/scripts`）**

- 一张卡片一个应用：应用名、状态标（`已加入` / `未加入` / `已停用`）、说明、
  `宿主机 <根目录>`、`N 命令组 · N 成员`，底部「查看详情 →」；
- 顶部可搜索：按**应用名 / 说明 / 根目录**过滤（纯前端过滤，输入即筛）；
- `新建应用` 打开编辑弹窗；保存成功后**直接进新应用的详情页**，省一次点击。

**详情页（`/scripts/:appId`）**

- 顶部 `← 返回脚本部署`；
- 标题区：应用名 + 状态标、说明、`宿主机 <根目录>`；
  右侧操作按权限给：`执行命令` / `加入应用` / `成员 N` / `编辑` / `停用` / `删除`
  （创建者与平台管理员才有后三个；非创建者但已加入的可 `退出应用`）；
- 一张 `未加入` / `已停用` 的提示条说明为什么命令执行不了；
- 「命令组」区逐条列出命令名、说明、命令主体、参数名，每条右侧一个 `执行`。

**建应用**

1. 列表页 `新建应用`；
2. 填**应用名**、**根目录**（执行前会 `cd` 到这里，须在白名单内）、说明（可选）；
3. 「命令组」区默认已有一个，点 `+ 添加命令组` 可加任意多个。
   每个命令组填：**命令名**（如「部署到测试」）、说明（可选）、**命令主体**（如 `python3 iwiki.py deploy`）；
4. 命令组内需要参数就「+ 添加参数」，逐个填：参数名（如 `--target`）、显示名、
   输入类型（文本 / 下拉选择）、取值方式（带值 / 开关）、默认值、是否必填；
5. 命令组可用 `↑` `↓` 调顺序（决定详情页里命令组的排列顺序）；
6. 保存。创建者自动成为应用成员。

**执行**

1. 详情页找到要跑的命令组，点它右侧的 `执行`
   （顶部 `执行命令` 等于执行第一个命令组）；
   若还没加入应用，`执行` 按钮是禁用的 —— 先点右上角「加入应用」自助加入；
2. 抽屉顶部的命令组标签可随时切换（切到别的命令组，参数表单同步切换）；
3. 左侧填参数 —— 留空即不传该参数；带开关的命令组勾选才拼 `--flag`；
4. 「即将执行的命令」实时显示拼接结果，**执行前就能看到最终命令行**；
5. 点「执行」，右侧控制台实时刷输出（彩色 / 语义高亮）；执行中可「终止」，
   可「复制全部」把输出带走；执行历史点任意一条回看，右侧也有单条复制；
6. 关掉抽屉**不会**打断宿主上的脚本，历史里点回那条 `执行中` 的记录即可重新接上输出。

参数变化只影响本地预览，不会发请求；预览与后端执行用的是同一套拼接规则。

**「在哪跑」怎么看**

- 列表页卡片、详情页标题区、抽屉头部都写着 `宿主机 <workdir>`；
- 抽屉里「执行位置」面板给出完整路径（可一键复制），并说明命令是经 `nsenter`
  进宿主命名空间执行的，不是跑在平台容器里；
- 「即将执行的完整命令」把**目录**和**命令**分两行列出，
  实际下发的完整脚本是 `cd '<workdir>' && <命令>`，点「复制」拿到的就是它；
- 执行历史**每条**都带 `cd '<workdir>' && <命令>` 和本地时间，
  回看时不用逐条点开猜。

**成员**

详情页右上「成员 N」打开成员弹窗：看谁在应用里、谁是创建者。
创建者可以移除成员；加入的人自己可以「退出」（创建者不能退）。

### 8.1 手机端

移动端单独调过，不是「能挤就挤」：

- **抽屉全屏**（`width: 100vw` + `100dvh`）：`96vw` 在手机上会留一条 4% 的缝容易误点到底层页面；
  用 `dvh` 是因为 `100vh` 是地址栏收起时的高度，地址栏可见时抽屉底部会被压到屏幕外、固定操作区点不到；
- **抽屉头部两行**：第一行标题 + 关闭，第二行命令组标签铺满整行横向滚动
  （原来标签被限制在 40% 宽里，4 个命令组基本没法点）；
- **触控目标 ≥36~44px**：所有按钮、命令组标签、参数开关、复选框；
- **抽屉单栏改 flex 纵向流**：原来用 grid 的 `auto` 行 + 子项 `min-height: 0`，
  会把左栏压扁、内容"溢出"盖到右栏上（实测「执行」按钮被历史面板挡住点不到）；
- **控制台给足高度**（`min-height: 46vh`），输出是手机上最想看的东西；
- **关键路径不截断**：`宿主机 <目录>`、抽屉头部的执行位置在窄屏折行显示而不是省略号；
- 详情页命令组在窄屏从「左内容 + 右按钮」变成上下排列，`执行` 按钮通栏 44px；
- 编辑弹窗参数表单改单列（6 个字段两列在 390px 下每个只有约 150px）。

## 9. 排障

| 现象 | 原因 / 处理 |
| --- | --- |
| 报「根目录必须位于允许范围内」 | 根目录不在 `SCRIPT_ALLOWED_ROOTS` 内，改路径或调大白名单后重启服务 |
| 报「根目录不存在：…」 | 保存时在宿主机上没找到该目录（注意判的是**宿主机**，不是容器里；容器里同名路径是另一个目录） |
| 报「根目录解析后不在允许范围内：A → B」 | A 是白名单内的**符号链接**，解析后落到了 B（白名单外）。要么把根目录改成真实路径，要么把 B 加进白名单 |
| 报「无法在宿主机上校验根目录（执行器不可用）」 | 保存时的宿主校验走的是与执行同一套「特权容器 + `nsenter`」，这条报错说明 `docker` / 镜像不可用 —— 此时脚本本来也执行不了 |
| 报「当前已有 N 个脚本在执行」 | 撞到并发上限，等前面的跑完，或调 `SCRIPT_RUN_MAX_CONCURRENT` |
| 提示「无法启动执行容器」 | 容器里 `docker` 不可用，检查 `docker.sock` 挂载与 `SCRIPT_RUN_IMAGE` 能否拉取 |
| 一点「执行」就失败、输出为空 | 先看 `docker run … nsenter` 是否可用：宿主执行 `docker run --rm --pid=host --privileged busybox nsenter -t 1 -m -u -i -n -p -- echo ok` |
| 输出中途没了 | 单次输出超 512KB 被截断（日志里会写明），属预期保护 |
| 服务重启后历史里出现「已中断」 | 正常 —— 进程没了，执行中的记录不可能再有结果，启动时会被标记 |
| 宿主机上出现 `sdpy-script-*` 残留容器 | 服务启动会自动清；也可手动 `docker rm -f $(docker ps -aq --filter name=sdpy-script-)` |
| 执行结果对但页面没实时输出 | 检查是否误把断连监听到挂到了 `req` 上（见 §4.4 踩坑记录） |
| 手工删库后残留孤儿 `script_commands` / `script_params` / `script_app_members` | **用 `sqlite3` 命令行走 CLI 时外键默认是关的**（`PRAGMA foreign_keys` 返回 0），`ON DELETE CASCADE` 不生效。要么删前先执行 `PRAGMA foreign_keys = ON;`，要么直接删 `script_apps` 由应用自己的 DELETE 接口处理（已开启外键并回归验证过级联） |
